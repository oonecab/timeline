# TIMELINE-SPEC v1.1.2：修正依据与实现解释

[TIMELINE-SPEC.md](../TIMELINE-SPEC.md) 是权威构建规格。用户修订的 v1.1.1 已解决归档搬运条件冲突，v1.1.2 已明确预算不可行错误；本文保留历史推导，并说明当前实现边界与回归设计。本次没有修改用户规格、数据库格式或 MCP 工具集版本。

## 1. 预算中的 tokens 含义

§4 的 `tokens(node)` 返回路径前缀和，§5 预算伪码中的 `tokens(id)` 必须理解为**该节点消息自身的 tokens**。否则第一步就会把目标之前的全部路径计费，随后又重复计费。公开 `Timeline::tokens` 始终 O(1) 返回 `prefix_tokens`；预算使用 `message.tokens`。

## 2. 预算不可行与多间隔修复（v1.1.2 已解决契约冲突）

v1.1.0 的 §5.2 字面伪码无法对所有输入满足 §5.3：目标及 pin 恒保留、每个省略区间放入一个 32-token 占位，同时总数不超过 `max_tokens + 32`（只允许 pin 本身超预算例外）。以下输入不存在满足全部要求的结果：

- 单节点目标成本 100，预算 0，没有 pin：保留目标就超过 32。
- 链成本 `[1000, 1(pin), 1000, 0(target)]`，预算 1：保留 pin 与目标时必须放两个占位，最低成本为 `32 + 1 + 32 = 65 > 33`；pin 本身并未超预算。

v1.1.2 §5.5 已规定保证优先于参考伪码，输入不可行时必须显式报错。实现保留 pin 本身超预算例外。其他场景先执行参考贪心选择；若实际输出超限，计算最低可行成本：强制保留消息成本，加上每个非空可省略间隔的 `min(原文成本之和, RESERVE)`。若最低成本仍超限，返回精确消息 `budget infeasible`，并附带 `{required_tokens, max_tokens}`。`required_tokens` 为最低布局总成本，不是超出预算的差值；上述第二个反例为 `{required_tokens:65,max_tokens:1}`。失败**不分配节点、不消耗 ID、不写审计或幂等结果**。

若最低成本可行而参考贪心超限（例如多处 Tier 2 节点拆开省略区间），以最低成本布局为起点，按 Tier 2、Tier 3 顺序尝试加入可选消息。每次按消息成本及相邻省略区间的合并/拆分，O(1) 计算实际成本差。仅接纳不突破上界的选择。此修复保持 O(路径长)，符合 §5.5 对等价修复循环的许可。

回归设计：`axiom_budget_bound` 检查 1000 个可行随机场景并断言规格反例的错误消息及载荷；`one_thousand_budgets_match_independent_feasibility_and_required_messages` 另检 1000 个包括真实摘要、pin 及不可行情形的随机场景，用独立最小成本计算区分成功与明确拒绝。CLI/MCP 真实进程测试分别验证 `{"error":"budget infeasible","data":{…}}` 和 JSON-RPC `error.{code:-32000,message:"budget infeasible",data:{…}}`，并验证失败后持久状态未变。

## 3. 占位覆盖与重复预算

若自动占位也作为 Tier 2 语义枢纽，10 条各 50-token 消息、预算 150 的首次调用会覆盖 n1..n7；再次调用优先保留其中旧节点，又为不同区间创建两个占位。输出变成 214，既超过 182，也违反重复调用不膨胀要求。

实现保留两份派生索引：`covers` 包含所有摘要（用于水位完整性与引用计数）；`semantic_covers` 仅包含真实摘要（用于 Tier 2）。占位不会改变下一次调用的语义优先级。同一状态下相同预算结果和占位 ID 完全一致，包括重新载入数据库后。

## 4. 不可变回填、版本链与幂等

§12 提到回填复用原节点，和 §3.4 的 `message` 永不改变冲突。实现优先保护不可变历史：回填生成同区间真实摘要的新节点，旧占位保留；归档判断将已有同区间真实摘要的占位视为已解决。显式 `supersede` 只能指向同区间真实摘要的最新版本；同一请求重复返回已有版本，其他请求不能让版本链分叉。

§4 的“所有变更同参幂等”与 `append/create` 的追加语义、`fork` 重名报错和 `drop_branch` 不存在报错冲突。实现采用具体操作契约：pin/unpin/switch 为状态幂等；summarize 按区间、文本、tokens、derived_from 和 supersede 去重；create/append/fork/drop/archive 等通过可选幂等键去重。无 key 的两次 append 代表两条消息。键以 timeline 为作用域，create 使用独立作用域。

## 5. 水位完整性优先于 unpin

水位可凭 pin 推进；若随后取消尚无摘要覆盖的 pin，就会违反完整性且不能通过回退水位修复。因此这种 unpin 返回错误，要求先摘要覆盖该节点，再取消 pin。所有其他 unpin 正常执行。

批量占位创建后，仅用一次原路径扫描推进到首个裸节点之前最远的新占位终点，保持逐个创建的水位效果与线性复杂度。

## 6. 归档冷热搬运（v1.1.1 已解决契约冲突）

v1.1.0 条款曾使可搬运集合恒为空，推导如下：

1. 可归档分支的整条路径位于水位之前。
2. 水位之前每条消息必须被 pin 或被摘要覆盖。
3. 归档条件要求路径没有 pin，所以每条消息都被摘要覆盖。
4. 可搬运节点又要求“无摘要覆盖”，因此符合搬运条件的消息集合为空；根节点由仍存在的当前分支共享，也不能搬运。

v1.1.1 已移除第 4 步的“无摘要覆盖”限制。当前实现仍逐项判断三条件、拒绝当前分支归档；成功时删除分支指针并写入审计，将路径中热区的独有无 pin 原文节点搬到 `archive`。摘要节点始终留在热区；摘要覆盖不阻止原文搬运。共享节点不动，已在冷区的节点不重复搬运，也不再次出现在本次 `archived` 中。归档不删除原文、不减少总节点数，也不承诺压缩同一 JSON 文件的大小。

`parent`、`children` 和消息不随搬运改变，因此允许热摘要指向冷区父节点。节点查找、路径、原文上下文、前缀和、区间及派生索引按冷热区联合结构读取和重建；源数据的父子对应、无环、摘要区间、分支、水位和版本链约束继续验证。直接从冷节点 fork 拒绝；从热摘要 fork、追加以及读取其归档祖先可正常工作。显式恢复冷节点的操作仍预留给 v1.2。

回归设计：覆盖非空独有原文搬运、共享节点保留、摘要留热、热摘要父节点转冷、原文不可变、归档审计及重启后冷热查询；随后从热摘要分支追加并再次归档，确认只报告新搬运节点。仍测试 pin、未回填占位、水位和当前分支拒绝条件；CLI/MCP 归档返回实际搬运 ID，并可据 ID 继续查询原文。

## 7. 推荐优化与平台验收范围

- §5.4 水位快速扫描为可选优化，当前**未启用**。`context_budget_with_watermark(..., enabled)` 的两个选项均走同一完整扫描算法，等价性测试通过不能证明存在优化加速。
- 增量 checkpoint 为可选项，当前每次成功事务保存完整原子快照，不维护操作 replay 文件。
- Unix 使用 `0600`；Windows 使用受保护的仅所有者可访问 DACL。本次验收在 Windows 执行；Unix 权限分支有条件编译测试，但未在本次环境运行。
- v1.1.1 已将 §13 第二项“6 条不变量”修正为 10 条。测试覆盖结构、前缀和、分支、区间、不可变源数据、水位、引用计数和版本链；O(1) `tokens` 由直接字段读取实现，不靠计时测试推断。

可执行回归见 `tests/axioms.rs`、`tests/adversarial.rs`、`tests/spec_v112.rs` 和 `tests/interfaces.rs`；实际执行结果统一记录于 [ACCEPTANCE.md](ACCEPTANCE.md)。本次文档影响覆盖预算错误契约、归档规则、冷热兼容边界及回归设计；技术栈、环境变量和部署方式均未变化。
